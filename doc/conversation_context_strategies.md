# 对话上下文管理策略

> 适用模块：`Hify.Modules.Conversation`（对话引擎）。
> 背景：LLM 本身无记忆，多轮对话靠应用层每轮重新拼接历史实现。详见 [conversation_streaming_sequence.md](conversation_streaming_sequence.md)「编排准备」阶段。

## 核心矛盾

上下文管理要在两端之间取舍：

- **模型上下文窗口有限**（见 `model_provider.model.context_window`），历史越多迟早超窗。
- **每轮重发要花钱、花延迟**：第 N 轮会把前 N-1 轮全部当 `prompt_tokens` 再算一次。

目标：在有限 token 内让模型"记得"足够多。

## 五种常见策略

### 1. 全量保留（不管理）

所有历史每轮原样带上，直到撞窗口报错。

- ✅ 实现零成本；信息无损，模型看到全部细节
- ❌ 迟早超窗直接报错；对话越长每轮越贵越慢；长对话不可用
- 适用：demo、明确很短的对话

### 2. 滑动窗口（Sliding Window）

只保留最近 N 轮 / 最近 N 个 token，更早的直接丢弃。

- ✅ 实现简单（截断即可）；token 量恒定可控，成本/延迟封顶；最常用
- ❌ 硬失忆——超窗的早期信息彻底丢失；按轮截断可能切断完整的工具调用循环
- 适用：绝大多数 MVP；近期上下文比远期重要的闲聊型对话

### 3. 摘要 / 压缩（Summarization）

把较早的历史用 LLM 总结成一段摘要，只带摘要 + 最近几轮原文。

- ✅ 有限 token 内保留长程"要点"；对话可无限长
- ❌ 摘要本身要额外调一次 LLM（多花钱、多延迟、可能引入事实错误）；有损，数字/原话会被磨掉；触发时机与摘要长度要调参
- 适用：长对话且早期信息重要（长任务、咨询）

### 4. 滑动窗口 + 摘要（Hybrid，生产常用）

最近 K 轮保留原文（精确），更早的滚动摘要成一段（概要）；窗口滑动时把滑出的内容增量并进摘要。

- ✅ 近期精确 + 远期概要兼顾；token 可控又不硬失忆；工业界主流
- ❌ 实现最复杂（维护摘要状态、增量更新、定 K 与阈值）；仍有摘要的有损问题
- 适用：需长对话体验的正式产品

### 5. 历史向量检索（RAG over History）

把每轮历史也做 embedding 存储，按当前问题相关性检索最相关的几段带上，而非按时间。

- ✅ 可跨很远召回相关内容；token 用得精准
- ❌ 实现重（历史也要切块/embedding/存向量）；可能漏掉时间连续但语义不相关的上下文；检索不准会带错；对短对话过度设计
- 适用：超长对话 + 有"翻旧账"需求；通常叠加 1-4 使用

## 对比速览

| 策略 | 实现复杂度 | token 成本 | 信息保真 | 额外 LLM 调用 |
|---|---|---|---|---|
| 全量保留 | 极低 | 失控 | 无损（直到崩） | 无 |
| 滑动窗口 | 低 | 恒定 | 近期全、远期丢 | 无 |
| 摘要 | 中 | 中 | 有损概要 | 有 |
| 窗口+摘要 | 高 | 可控 | 近期全+远期概要 | 有 |
| 历史 RAG | 高 | 精准 | 相关召回、易漏 | embedding |

## Hify 的选型决策

按"简单性原则 + MVP（内部 20-50 人）"：

- **一期：滑动窗口（策略 2），按 token 预算截断**（非按轮数）。
  - 实现简单、成本可控、无额外 LLM 调用，小规模够用。
  - 落地：用 `model.context_window` 减去 `max_output_tokens` 与 system 提示词，得到留给历史的预算，从最新往回塞到塞满。
  - **坑**：按 token 截断时不能把 `assistant(tool_calls)` 和对应的 `tool` 结果消息拆开——要么整组保留要么整组丢，否则模型看到"调了工具却没有结果"的残缺序列。靠 `conversation.message` 的 `tool_calls` / `tool_call_id` 字段判断成组边界。
- **二期（出现长对话痛点时）：升级到窗口 + 摘要（策略 4）**。增量演进，不必推倒重来。
- **历史 RAG（策略 5）**：当前定位下属过度设计，暂不做。
